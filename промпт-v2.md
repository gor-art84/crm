6. Критерии готовности — как я пойму, что шаг сделан (что увидеть в Apollo Sandbox / psql / redis-cli / браузере).

8. Чего не делать.
9. Подсказка по отладке — симптомы и куда смотреть.

ПРОДУКТ И ДОМЕН (без изменений)
==================================================

CRM для учебного центра. Публичный сайт — витрина программ; эта CRM — внутренняя система менеджеров и методистов.

Роли:

1. Administrator (ADMINISTRATOR, суперадмин)
   - пользователи, роли, доп. права, справочники, настройки
   - видит всё, включая глобальный журнал аудита
   - не является основным оператором сделок

2. Manager (MANAGER, менеджер)
   - клиенты, сделки, оплаты, внутренние документы
   - заводит клиента
   - ведёт сделку до передачи методисту и после возврата (закрывающие документы, оплаты)

3. Methodist (METHODIST, методист)
   - образовательные программы, категории, сроки обучения, доп. информация по программе
   - принимает сделку с канбана, ведёт обучение, по завершении возвращает менеджеру

Права: три базовых набора по роли (`ROLE_PERMISSIONS`) + индивидуальные доп. права (`UserPermission`), которые администратор выдаёт галочками. Пример: методист, который также продаёт, получает `CLIENTS_WRITE` и `DEALS_WRITE`. Новые сущности добавляют пары `X_READ` / `X_WRITE` в enum `Permission` и в карту ролей.

Клиенты (Client) — это ПЛАТЕЛЬЩИК, не «человек в обучении»:

- LEGAL_ENTITY — юридическое лицо. Обучает своих сотрудников. У юрлица есть контактные лица (бухгалтер, кадровик) — они НЕ обязательно слушатели.
- INDIVIDUAL — физическое лицо. Может оплачивать обучение себя ИЛИ другого человека (плательщик ≠ слушатель).
- INDIVIDUAL_ENTREPRENEUR — ИП. Реквизиты как у организации через DaData party, но это не ООО. Хранится в той же таблице `Client` с `type = INDIVIDUAL_ENTREPRENEUR`; в логике не смешивать с LEGAL_ENTITY (ИНН 12 знаков, нет КПП, обязателен ОГРНИП).

Важно: канбан и статусы живут на СДЕЛКЕ (Deal), не на клиенте. Один клиент (особенно юрлицо) может иметь много сделок. Не делать общий «статус клиента» (поле `Client.status` — это статус юрлица из ЕГРЮЛ, не стадия работы).

Сделка (Deal) — единица работы:
- кто плательщик (клиент: юрлицо / ИП / физлицо)
- какие программы (множественное число — в модели сразу связь many-to-many / DealProgram, даже если первый UI упрощён; подтвердить на развилке 4)
- какие слушатели (DealLearner)
- какие документы
- какая стадия канбана
- кто сейчас ответственный (менеджер или методист)

Слушатель (Learner):
- для юрлица: сотрудник организации; кадровые/учебные поля (ФИО, должность, дата рождения, СНИЛС/паспорт). Состав полей вводим итеративно: на старте минимальный набор + пометка «дополним позже»
- для физлица: слушатель может быть самим плательщиком или другим человеком

Контакт (Contact) — контактное лицо клиента (для LEGAL_ENTITY точно; для ИП — развилка 3). Это не User и не Learner.

Программы — иерархия как на https://www.standart82.ru/ (ориентир домена, сайт НЕ парсить и не импортировать):

Уровень 1. Вид программы (фиксированный enum, не свободный справочник):
- QUALIFICATION_UPGRADE — повышение квалификации; документ по итогам: удостоверение о повышении квалификации
- PROFESSIONAL_RETRAINING — профессиональная переподготовка; документ по итогам: диплом о профессиональной переподготовке
- PROFESSIONAL_TRAINING — профессиональное обучение; документ по итогам: свидетельство / удостоверение с разрядом

Уровень 2. Категория внутри вида (справочник методиста). Примеры с витрины — ориентир, не каталог для парсинга:
- ПК: охрана труда, экологическая безопасность, пожарная безопасность, работы на высоте, электробезопасность, антитеррористическая защищённость
- Переподготовка: охрана труда, образование и педагогика, кадры, экология, ИТ и сети, психология, физкультура/спорт/туризм, пожарная безопасность, юриспруденция, транспорт
- Профобучение: железнодорожный транспорт, рабочие профессии, строительство и ЖКХ, связь/телеком/ИТ, транспорт

Уровень 3. Конкретная программа (Program): название, объём часов, формат (очно/заочно/дистанционно), итоговый документ, присваиваемая квалификация/разряд (опционально), сроки, цена, активность.
Методист создаёт и редактирует программы. Детальные учебные поля «добавим позже» — в схеме сразу заложи расширяемость, но не выдумывай 40 полей заранее.

Цена и оплаты: НЕ float. Либо `Decimal` (`@db.Decimal(12, 2)`), либо целые копейки (`Int`/`BigInt`). Конкретный вариант зафиксировать на Итерации 8, не откладывать.

Канбан (первый рабочий набор стадий):

Менеджер:
- NEW — новая сделка
- DOCUMENTS — подготовка заявки / договора / счёта
- WAITING_PAYMENT — ожидание оплаты
- READY_FOR_METHODIST — готово к передаче

Методист:
- IN_TRAINING — обучение
- TRAINING_COMPLETED — обучение завершено

Снова менеджер:
- CLOSING — акт, закрытие, выдача/отправка документов
- DONE — закрыта
- CANCELLED — отмена

Правила перехода:
- менеджер двигает только свои стадии и передаёт методисту
- методист двигает только свои и возвращает менеджеру
- админ может всё
- переход логировать в АУДИТ (кто, когда, из какой стадии, в какую, комментарий). Без STATUS_CHANGE канбан не считать готовым.
- правила переходов живут ТОЛЬКО в NestJS-сервисе; Next их не дублирует.

АУДИТ (КТО / ЧТО / КОГДА) — ближайшая большая тема
==================================================

Администратор видит ленту и карточку сущности:
- кто (userId, email snapshot, роль на момент действия)
- когда
- действие: CREATE | UPDATE | DELETE | LOGIN | LOGOUT | LOGIN_FAILED | STATUS_CHANGE | DOCUMENT_GENERATED | …
- сущность: Deal, Client, Contact, Learner, Program, Payment, Document, User, …
- entityId
- diff для UPDATE: before / after только изменённых полей
- для DELETE: снимок удалённой записи (без секретов и без password hash)
- requestId / correlationId
- опционально IP и user-agent (для login)
- комментарий при смене стадии канбана

Аудировать обязательно: клиенты, контакты, слушатели; сделки и переходы канбана; оплаты; документы; программы/категории; пользователи, роли и доп. права (включая `deactivateUser`); логин / логаут / неуспешный логин (без пароля).

НЕ аудировать: таблицу AuditLog саму себя; read-only списки и DaData lookup; секреты, хеши паролей, сырой API-ключ, сырой DaData.

Порядок реализации:
- Шаг A (4.2). Модель `AuditLog` в `prisma/audit.prisma` + `AuditService.log()`. Я ВРУЧНУЮ вызываю его в `login`, `logout`, `createClient`, `deactivateUser`, чтобы понять контракт. Запись аудита в той же транзакции, что и изменение (`prisma.$transaction`).
- Шаг B (4.3). Общий механизм: requestId на входе (middleware, заголовок `x-request-id` или `crypto.randomUUID()`), actor через `AsyncLocalStorage`, куда `GqlAuthGuard` кладёт `userId`; Prisma Client `$extends` на create/update/delete/upsert для CUD-аудита с diff.
- Шаг C (4.3). Экран админа `/audit`: фильтры по пользователю, сущности, действию, дате, entityId. Позже — вкладка «История» на карточке (развилка 2).

Надёжность: audit insert не должен падать молча; UPDATE без diff бесполезен — учить сравнение old/new и отбрасывание `updatedAt`; JSON-снимки разумного размера. Trade-off «транзакция vs outbox» — отдельный урок позже. Случайный npm `nestjs-audit-*` не ставить, пока не понята своя модель.
